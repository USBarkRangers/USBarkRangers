# Implemented native architecture — phases 1–3

This document maps **implemented** responsibilities. Future files remain proposals in [the full file map](../../04-docs/plans/ios-native-2026-09-09/SWIFT_FILE_MAP.md). Build each phase only after the user explicitly starts it. The app uses Swift 6, iOS 18.4 minimum, SwiftUI, a Foundation-only BarkDomain package and native MapKit. Phase 3 adds Firebase Auth/Firestore/Functions, account-scoped SwiftData and concrete profile/mapStyle receipts. No migration framework, background location mode or custom tile downloader exists. The account graph is independent of catalog loading.

## Read this path first

`BarkRangerApp → AppComposition → AppLifecycle / RootView`

Startup follows `StartupModel → CatalogRepository → CatalogDiskStore / CatalogHTTPClient / CatalogValidator`. The repository publishes immutable accepted revisions to discovery and settings. Discovery follows `MapFeatureModel → ParkResults.compute (off MainActor) → ParkSearchIndex + ParkFilter → one immutable matching-ID/park projection → MapScreen → MapSearchBar / FilterChipsView / MapSearchResults / NativeMapView → MapCoordinator`. Details follow `MapScreen → ParkDetailSheet → ParkDetailView → ParkDetailMetadata / ParkDetailActions / ParkThumbnailStrip / ParkDetailContent`; selection passes an accepted Park synchronously to ParkDetailModel, and directions use `ParkDetailModel → MapsHandoff`. `ParkSheetLayout` owns snap heights, and `MapSelectionFraming` uses one medium-safe selected-pin anchor for both low and medium. Views never fetch catalog bytes, count map clusters, or write persistence directly.

## Deliberate boundaries

The app's live manifest URL is empty until authorized provisioning. Local fixtures verify updates; that is not proof of live sheet triggers, IAM, public object delivery or cellular latency. While the app is active, successful regular freshness checks occur at most once per minute; reconnect/manual requests obey coalescing/backoff/Retry-After. iOS suspension is not a background polling promise.

The 3-second startup decision is separate from the 10-second request deadline. The stream's accepted state is published only after complete validation and atomic commit. Camera, filter choices and selected identity do not reset when catalog metadata changes. Retired/unresolved records are never silently reassigned by coordinates. The native catalog has no personal-data dependency, and phase 2 does not move users or change deployed web/backend behavior.

## Focused audit corrections — 0.2.5

The editable sources are `SettingsRepository.value.filters` for search/filter input and `ParkDetailModel.park` for selection. Result input keys, the accepted immutable search index, catalog-ID set, annotation objects and framing keys are derived projections or comparison caches. None can edit or persist another query/selection independently.

`DiscoveryStateTests` exercises exact computation counts, external reset, accepted revision versus status-only changes, controlled late completions, selection/refresh/directions agreement, queued manual refresh and immediate foreground restart. `DiscoveryPerformanceTests` measures 393/5,000-record projections and counts actual MapKit lookups/mutations during 300 geometry-only updates. `DiscoveryTestSupport` owns isolated temporary catalogs/preferences and the controlled completion gate. `CatalogDiagnosticsTests` verifies emitted failure categories and retained fallback. `LocationCancellationTests` substitutes a concrete CLLocationManager to verify queued cancellation and request replacement without requesting real permission.

LocationClient tags cancellation with the exact request identity; MapFeatureModel retains a cancelled locate task until its own cleanup completes, preventing old cleanup from clearing a replacement. Startup’s decision task checks cancellation again after the catalog actor read. SettingsModel owns manual refresh tasks; its view expresses one synchronous intent. These are corrections to existing Phase-2 lifetime ownership, not a new task framework.

The explicit background-execution choice follows [Swift SE-0461’s `@concurrent` contract](https://github.com/swiftlang/swift-evolution/blob/main/proposals/0461-async-function-isolation.md), which matters with this project’s approachable-concurrency setting. No detached task, worker singleton or new protocol hierarchy is introduced.

## Adding a device preference

Keep the current typed path: `SettingsView binding → SettingsModel.update → SettingsRepository.update → interested feature`. A control changes one value; it does not imperatively refresh the map, recompute search, clear selection or coordinate future cloud writes. The sanitized repository value remains authoritative. Broad Observation notifications are acceptable while feature-specific equality gates prevent expensive unrelated work; the current computation-count and native-marker tests enforce that boundary.

For each new preference: add its typed value/default, CodingKey and compatible decoding in AppSettings (or Query for filters); put validation in `sanitized` when needed; add one real control only when an implemented consumer exists; apply effects in that feature's existing owner; test older saved data, relaunch/reset and unrelated-work invalidation. Keep persisted enum identifiers stable. Add a small nested preference group when a coherent group actually grows; avoid a dynamic registry, property-wrapper framework, global event bus or one callback per affected subsystem. Account settings, entitlements and trip/visit data do not belong in this device store.

`SettingsTests` verifies saved-value evolution, successive edits, relaunch/reset, camera removal when remembering is disabled, native map-style/overview effects, actual connection loss/recovery and transient map-loading failures without extra queries or selection/camera changes. `SettingsUITests` exercises the real controls and persistence. `ParkDetailSheetUITests` covers body-drag resize versus high-only scroll and native tab restoration. `MapPresentationTests` checks rendered threshold-animation completion/reversal, reduced motion and inactive-map cleanup.

## Isolated development entry points

The shared scheme’s Test action sets `BARK_ISOLATED_APP=1`; each UI test supplies a unique `BARK_TEST_SCOPE` UUID. Both catalog cache and preferences are scoped. Reusing that UUID deliberately tests relaunch persistence; UI sandboxes are disposable Caches data and never share `Application Support/BarkCatalog`. App-level tests use AppSandbox and await `lifecycle.stopAndWait()` before `removeArtifacts()`, including failure paths. A malformed scope still creates an isolated scope; a non-loopback fixture URL is rejected. Previews use memory-only preferences, no HTTP, no location permission requests and no external handoffs.

Phase 3 extends this construction boundary with an explicitly selected demo Firebase assembly. The ordinary test/preview path still has no accounts. The emulator-backed SDK tests verify UID separation and offline persistence; actual Apple/Google provider registration and device checks remain separate prerequisites. Device preferences remain independent of UID-scoped storage and sync.
