## iOS-only rebuild — connected account, trips, visits and walks, September 14

The historical build notes below describe the previous backend. The native backend is deployed to the isolated bark-ranger-ios project as of September 14; it is not an accepted production replacement. Its current execution record is [IOS_NATIVE_REBUILD_PROGRESS](../../04-docs/operations/IOS_NATIVE_REBUILD_PROGRESS.md), with deployment/device evidence in [IOS_NATIVE_CLOUD_ACCEPTANCE](../../04-docs/operations/IOS_NATIVE_CLOUD_ACCEPTANCE.md).

The connected account path is now `AccountView / SettingsRepository → AccountModel / NativeProfileFeature → NativeStore profile rows + durable intents → NativeProfileSync → NativeProfileCloud → nativeCommand`. Confirmed profile, visible local edits and server-confirmed access stay separate; none is copied into `PersonalSnapshot` or `UserValue`. `AccountSession` remains the single identity/lifecycle owner. It clears the visible scope immediately, cancels/drains and closes the old feature, and only then opens the next. `NativeSyncJobs` owns shared job cancellation, not whichever caller happens to await it.

The old `LocalStore`, account blob/schema, cloud reader/listeners, `SyncEngine`, legacy repositories and old-format domain models have been deleted, including their DEBUG entry point and guest-file importer. Native visits, walks, trips and profile use one scoped `NativeStore` transaction writer. Guest drafts use that same native schema in a separate namespace; no historical account data is imported. Old account deletion/payment-provider code was removed; a native deletion service and Apple activation remain separate release prerequisites.

The connected trip path is `TripsView / RouteDaySheet → TripEditorModel / RouteDayEditor → ActiveTripSession → TripDraftSession → NativeTripRepository → NativeStore`. There is exactly one active editor in `AppComposition`. Screens do not select from raw saved records, sequence saves themselves, or reset the shared editing lifetime. `NativeTripFeature` owns metadata paging, pending-work scheduling and read readiness, not editable content. It reuses the profile scope's `NativeStore`; `NativeTripSync` uses reusable pause/drain/resume jobs and its own account-bound transport.

An edit checkpoints one draft and changes device selection only when necessary. Explicit Save creates a durable, revision-bound intent, seals its exact bytes before sending and commits the server result with cache/preimage changes. Later typing and trip switches are protected separately. An acknowledgment that only advances the base does not restart the editor or erase its save confirmation. Delete/conflict actions bind the reviewed values; conflict resolution also binds exact operation IDs. Remotely deleted work is explicitly recovered under a new trip ID. Ordinary identity changes refuse to proceed on a failed checkpoint. Forced authentication changes hide private edits and retain an unsaved buffer in memory for its original scope; this cannot survive process death if storage is unavailable, and the UI says so.

Library requests return ten metadata rows, not itinerary/current notes. `ActiveTripSession → NativeTripRepository` owns detail demand and reuses an exact metadata-revision cache stamp (including remote note-only changes); the library feature no longer independently downloads selected detail on foreground or selection changes. The command worker omits preflight detail downloads but retains one canonical post-command read for concurrent untouched-note reconciliation. More metadata pages load on request; expired-cursor metadata bootstrap can still traverse the full archive, an outstanding cost issue. The durable cache retains 250 metadata rows plus selection and 24 clean details within 12 MiB; dirty drafts and pending intents are not cache entries. Completed replacement scans reset old presentation pages so expired deletions cannot remain as ghost rows. `TripDraft` has no raw `expected` value. `LegacyTripDraft` and the codec are confined to earlier-device recovery/historical adapters; successful guest import is receipted and is not repeated in steady state. The old `TripRepository` and account trip-paging hooks are DEBUG historical regression code, excluded from Release and never constructed by the native composition. The old whole-library presentation builder and map fallback were removed.

Existing stop-note-only Save uses `NativeTripNotes → saveTripNotes`, one atomic revision-checked batch rather than independent note requests. It reads/writes changed notes and small trip metadata, not itinerary/place documents; metadata and note revisions advance, itinerary revision does not. The existing durable queue understands this distinction for acknowledgment, successor preimages and deletion. Old full-save intents keep their original kind and sealed bytes. First-note references, day notes, mixed itinerary changes and conflict recovery retain the full atomic save. Full post-save confirmation still reads current notes, so the entire workflow is not constant-cost even when the mutation itself is proportional to changed notes.

Device bookmarks stay independent of accounts and trips. `SavedPlaceStore` owns original JSON records and a rebuildable SQLite R-tree index; `SavedPlacesModel` holds viewport pin metadata and at most one selected full bookmark. Original file/stop identities and notes are retained, including earlier hashes. Indexing does not rekey or upload files. Mark-before-write recovery rebuilds after interruption; malformed authored records fail closed. Region queries handle the date line and retain active/selected identities without an arbitrary pin cap. Notes are not marker payloads; note/time edits and repeated official stops do not retrigger bookmark point queries. Dense, world-sized map rendering is still a real-device measurement gate, not solved by hiding pins.

Visits use `ParkDetailModel / PassportModel → NativeVisitRepository → NativeStore → NativeVisitSync`; only compact official-site markers and confirmed progress are published account-wide. History requests fifty-row pages, and date/removal confirmations bind exact displayed revisions. The map overlays pending markers without adding pending points to confirmed totals. Walks use `ExpeditionModel / WalkRecorder → NativeExpeditionRepository → NativeStore → NativeExpeditionSync`. A recording's identity, original measurement and run attribution are immutable. Durable command handoff precedes temporary recording-file cleanup. Pending miles remain distinct from confirmed totals; completion waits for confirmed run credit. Historical conflicts affect their connected dependencies, not every future walk or trail selection.

`NativeFeatureSync` handles foreground coalescing, pause/drain and retry, not feature business rules. Activity reconciliation restarts an overtaken scan from its unchanged completed lower watermark, so a newer point read cannot skip another activity's change. Histories retain bounded reconstructible caches; extra display pages belong to the open history screen and are released when it closes. Missing cached selection is not treated as a server-confirmed empty expedition. Health import checks only the explicit candidate identities. Permanent tracks, journals, dogs and photos remain roadmap comments, not implemented features.

Native leaderboard requests return five public entries plus the signed-in user's standing. Higher-score counting is an index aggregation with one-minute private rank-cache reuse, not a full user-document download or fan-out rank rewrite. Its index-scan cost is **not constant** at 100K entries. CSV export is an explicit, revision-checked, page-at-a-time traversal to a protected temporary file; normal map/Passport loading does not perform it.

This remains a beta rebuild, not a release-readiness or 100K-user performance certification. Apple activation, native account deletion and future journal/media work are separate. Deployment and device status for the mailroom change are recorded in the report below.

**Sync fault isolation checkpoint: September 19, 2026.** [Sync rejection recovery and fault isolation](../../04-docs/reports/ios-native/SYNC_FAULT_ISOLATION_2026_09_19.md). One boundary rule: a bad remote response is `invalidReply` and may be isolated; bad local data is a storage or corruption error and ends the pass; the phone's own request faults are `invalidRequest`. Every cloud reports a reply of the wrong shape or one that breaks its contract as `invalidReply` (`NativeCallableTransport.decodeReply` and `validateReply`; the profile and progress readers do the same for Firestore documents). `NativeMailroom.isIsolatableRemoteResponseFailure` names only errors that cannot come from local rows, and `NativeMailroom.rejectionCodes` is the one definition of the shared refusals. `NativeIndependentSteps` lets the trip, visit, walk and saved-pin passes skip one failed step and still throw the first failure at the end; `NativeFeatureSync` is unchanged. The drain defers and continues past one operation's bad reply only in lanes that pass `isolatingRemoteResponseFailures` (visits, saved pins); that operation stays sealed and is never marked rejected. Trip and profile chains and the one-uncertain-walk rule are unchanged. A refused saved pin can be discarded with its never-sent suffix, the one exception to never-sent-only discard.

**Account hardening checkpoint: September 18, 2026.** [Account deletion and sign-up hardening](../../04-docs/reports/ios-native/ACCOUNT_DELETION_HARDENING_2026_09_18.md). `AccountSession` stays the only identity and lifecycle owner. One owned task, `removal(of:)`, serves the delete button, a server-confirmed `deleting` profile and `AccountIdentity.removedByServer`; Apple revocation runs inside it, before the server delete, and a dismissed screen cannot cancel it. There is no write-ahead deletion journal: the server's word settles a lost reply. Failed cleanup is a warning with a retry and never gates sign-in or the guest scope; only the deleted owner is fenced, by marker filename, and an unreadable marker is set aside. Account features open independently, and a failed guest-draft handoff no longer fails trips. A refused profile bootstrap is replaced on a forced refresh, reports no conflict, and is explained to the user. `IdentityChangeBlocked(reason:)` carries the trip editor's wording to the account notice. Adding a `NativeProfile` map style or status requires a shipped release with a tolerant decode first, because older versions read the profile and entitlement in one strict call. Account switching has one owner: `AppComposition` defines one `resetAccountScope` closure beside the models it builds, `AppLifecycle.accountChanged` runs it on a real change, and `RootView` keeps a single trigger. A new account feature adds one line to that closure. Deletion is a separate mechanism: data in the account's `NativeStore` or under its hashed folder is erased with that folder and needs no hook, and the `eraseAdditionalAccountData` closure covers only what cannot live there. That folder has one definition, `NativeAccountRemovalFiles.accountFiles(directory:uid:)`. Deferred items are listed under Known future architecture items in the report. 58 tests in 9 suites pass on the simulator; emulator-gated tests and all physical-device checks (App Attest, Apple revocation, deletion across two devices) await the owner.

`BarkRangerApp → AppComposition → AppLifecycle / RootView`

## Map search and trip commands — 0.4.21

One add path now serves catalog parks, custom places, Planner Add Stop/Add Below and trip bookends:

`Planner intent → TripEditorModel.searchOnMap → existing TripDraftSession checkpoint → StopSearchRequest → RootView → MapFeatureModel.beginAdding → RouteDaySheetViewModel.open → focused Map search`.

`Map query (SettingsRepository.filters.search) → ParkResults.compute for catalog results + MapPlaceSearchModel for native suggestions → ParkDetailModel.Selection → shared ParkDetailSheet / ParkDetailActions → MapStopActions → RouteDayEditor → TripRepository.addStop → LocalStore atomic save → AccountSession publication → membership / PersonalParkProjection / MapTripSession → DayRouteService → map renderers`.

| Owner | Boundary |
|---|---|
| `StopSearchRequest` | Immutable scope/trip/destination/anchor IDs. No editable trip, query, route cache or task. |
| `MapPlaceSearchModel` | Debounces/cancels suggestions and place resolution. Rejects stale results by generation. Coordinate entry works offline; online lookup retains Premium/connectivity policy. Camera-only changes do not restart search. |
| `MapSearchClient` | Native MapKit completion and resolution, bounded timeout/cancellation, supported custom-stop fields only. No persistence, permissions, UI selection or trip targeting. |
| `ParkDetailModel.Selection` | Exactly one selected park **or** place. Name, Directions target and trip actions derive from that value. No separate selected-place property in the search model. |
| `MapStopActions` | Stateless contextual action builder. Day membership and previous/next edits use shared domain policies and stable IDs. No draft, write task, renderer or manual color update. |
| `MapTripSession` (removed in 0.4.23) | Replaced by shared ActiveTripSession and derived TripRoutingModel; no independent Map trip remains. |
| `MapPlaceAnnotations` | Reconciles only custom place markers, stable stop IDs, day rings, selected numbering and one temporary selection. Geometry-only changes reuse annotations and images. No search, route calculation or stop edits. |

`TripDraftSession.draft` remains the only authoritative editable Planner buffer; `TripEditorModel.draft` forwards it. Map reads persisted checkpoints, Overview reads Planner's value, and no new component owns a competing editable draft. StopPickerModel and StopPickerView are deleted. Bookend identities remain distinct from ordinary day stops. Forward moves may atomically append the next day under the existing 50-day limit; stale menus and failed writes cannot leave a partial move.

Map's sheet uses current container safe-area geometry and ignores keyboard safe-area resizing. It no longer needs a cached tab-bar-overlap value that could remain zero when Add Stop opens Map for the first time. Existing detents, tab-bar animation, fixed-zoom pin framing and shared Planner/Map timeline stay intact.

This pass changes no Firebase functions, rules, schema, entitlement policy or cloud queue. Production rollout limitations from 0.4.20 still apply. New note/journal workflows should continue using narrow domain intents and the existing persistence boundary; do not grow MapFeatureModel or TripEditorModel with native search delegates, renderers or a second trip buffer.

### Endpoint presentation and cancelled trail choices — 0.5.4

`TripRoutePlan.bookendDays(in:)` owns endpoint placement: first/last populated day, or the first existing day when every day is empty. Route construction, `TripStopPolicy`, `TripDayEdit.removePark`, `PersonalParkProjection`, Planner, Map day sheet and Overview consume this pure derived rule. Adding an empty final day no longer presents the trip finish on a different day from its route and pin. No new model, cache, draft, persistence field or network work is introduced.

`ExpeditionView` owns the temporary trail choice and its confirmation presentation. Dismissing the confirmation clears the pending choice. The confirmation captures the chosen `Trail` for its action and visibly explains the progress reset; a later picker Done cannot revive a cancelled choice. `ExpeditionModel.assign` remains the existing mutation entry point.
