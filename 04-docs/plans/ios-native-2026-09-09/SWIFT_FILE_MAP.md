# Every proposed production Swift file

This is the complete proposed **production Swift** inventory, not a direction to create all files immediately. Tests, resources, Xcode/CI configuration, and backend files have separate inventories. All paths below, including `Packages/`, are relative to the proposed `01-code/ios/` directory. Phase 1 is now implemented there; see the [current ownership and call map](../../../01-code/ios/ARCHITECTURE.md) and [phase report](../../reports/ios-native/PHASE_1.md). The operations below still describe the full future contract; only the phase-1 subset exists so far.

Phase key: **1** foundation/app shell, **2** catalog/discovery, **3** accounts/persistence/sync, **4** visits/trips/passport, **5** expeditions/native capabilities, **6** purchases/integration. The phase column is the **first introduction**, not permission to implement every operation immediately. The [six implementation prompts](IMPLEMENTATION_PHASES.md) specify which operations arrive later and take precedence over the former sequence. Implement each file only when its phase needs it. “Budget” means estimated physical lines including comments/spacing, excluding tests, and is a sizing aid rather than a mandate.

Each row specifies the file's owned API, its behavior, and its allowed direct collaborators. A row's API list includes the planned public operations; synthesized initializers, protocol-required members, and obvious private formatting/layout helpers need no separate architectural layer. Pure policy files may declare private helper functions but cannot acquire side effects. View `body` properties render state and child views; actions call the listed model or supplied closure.

## File-level rules during implementation

Every production Swift file begins with a short purpose/ownership comment and uses names that explain the domain. Public operations document preconditions, returned errors, persisted effects and cancellation when relevant. Do not comment every obvious line or copy this entire plan into source headers.

Use roughly 150–300 lines as the usual review comfort range, not a mechanical maximum. The 340-line recording controller is acceptable if it only coordinates recording; adding entitlement formulas or map drawing there is not. Extract by responsibility when a file develops two reasons to change. Do not split a coherent algorithm into dozens of one-function files to meet a line target.

Do not create `Utils.swift`, `Helpers.swift`, `Managers.swift`, `GlobalState.swift`, a global event bus, a generic base view model, or `FirebaseService.swift`. Add a new function to the row that owns its behavior. If no row owns it, first record the new responsibility and its dependencies here.

Allowed future growth: new feature folders depend on repositories and domain rules, never on another feature's rendered view. Add a new storage field through LocalSchema and transport decoder changes; introduce an upgrade plan when an actual installed native schema needs conversion. Add a new paid feature to Entitlement's feature enum and server policy fixture. Add a catalog field through publisher schema, validator and Park value before any screen consumes it.

**Current build inventory: 105 production Swift files, 20,310 budgeted lines.** Stable IDs have deliberate gaps: D19, U03, U09, P19 and F13 were removed rather than reassigned. No archive importer, account migration model, separate legacy decoder or speculative native-store migration file is required. U12 owns normal decoding; U01 owns native schema definitions. The queue is a small fixed set of supported personal operations, not a generic synchronization framework.

The budgets in this document are summed in CODE_REDUCTION.md. They are forecasts; no implementation or benchmark has been performed.
